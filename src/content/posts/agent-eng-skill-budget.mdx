Agent 圈子里流行过一种很省心的迷思：工具挂得越多能力越强，Skill 文档写得越全系统越稳。给模型多塞一份说明，看起来像多配一件武器；多补一条 `NEVER` 禁令，看起来像多上一道保险。我以前也这么信，直到亲眼看着一次平平无奇的查询，把输入 token 从三千一路干到了三十八万。

那次执行的输入序列是：`3,106 → 30,526 → 55,105 → 380,178`。

凶手并不难抓：两次 Jira 全文搜索，`text ~ "split tips"` 和 `text ~ "tip allocation"`，入参顺手填了 `maxResults: 50`，接口热心地把 `description`、`comment`、`attachment`、`issuelinks` 全家桶一并端了回来，合计约 1.03 MB 直接倒进了 Agent 的 scratchpad。最冤的是 Postgres 里的 chat memory，一上来被我们当头号嫌疑人审了半天，捞出来一看只有 3 KB，纯属路过围观的无辜群众。

更阴的是故障被掩盖的方式：底层模型调用其实已经撞上 context window 上限报错了，但编排节点配了 `onError: continueErrorOutput`，把异常顺滑地导进了错误分支，整条工作流在监控面板上照样挂着绿油油的 `success`。你以为自己在监控业务成功率，其实只是在监控最后一个节点收工时的心情。

## 工具结果没有生命周期：「让模型自己摘要」救不了场

很多人看到上下文撑爆，第一反应是「扩窗口」或者「让 Agent 把长结果摘要一下」。这两个直觉在工程上都站不住脚。

真正致命的机制在于：**Agent 的工具返回值默认没有淘汰生命周期**。一次搜索吐出 1 MB JSON，绝不是模型「看一眼就扔」，而是从此在 scratchpad 里买房落户——后面每一轮推理，系统都得把这 1 MB 历史原封不动再喂一遍。第一轮它是单次开销，到第八轮就成了复利滚出来的定时炸弹。

至于「让模型自己做摘要」，时序上就错了：摘要发生在模型读完全文之后，而「读全文」那一刻上下文就已经炸了——拆弹专家还在路上，炸弹已经响了。下调 `maxIterations` 也只能当兜底，好比马路上的限高杆，拦得住绵延十公里的车队，拦不住一辆自己就长得像栋楼的矿山卡车。

![两阶段检索](https://bugyalu-1307401873.cos.ap-guangzhou.myqcloud.com/typora/skill-budget-explosion.png)

根治的办法是从接口契约上拆掉暴饮暴食的通道，把「找线索」和「调卷宗」切成严格的两阶段检索：

- **候选海选阶段**：强制收窄 JQL 范围（限定项目、issue type 或父任务），最多返回 5～10 条，且只准携带 `summary / status / issuetype` 这类户口本级别的轻字段，`attachment` 和 `issuelinks` 一律不准进门；
- **定点取证阶段**：筛出真正相关的两三个单号后，再按 issue key 逐条读取正文与评论。

从此这条规则成了我审所有 Agent 工具的固定问题：任何一个返回列表的工具，最重的一条记录有多大？调用方在九成场景下真的需要每一条的完整内脏吗？**返回体积上限不是实现细节，它本身就是工具契约的一部分。**

## 默认认知税：为什么 Skill 越补越笨

38 万 token 是工具返回值闯的祸，顺着这笔账往下查，我发现了另一笔更隐蔽的长期透支：**Skill 的默认认知税**——只要某个 Skill 被挂载激活，无论当前请求用不用得上里面的分支，模型每一轮都得把整套规则读完并纳入注意力权衡的固定成本。

我们的 Jira Skill 就是这么一口口吃胖的。最早它只有 `read / search / update / link` 几个干净的原子操作；后来团队为了堵流程漏洞，把「创建 Story 必须配套写 Release Note」的整套规矩塞了进来：字段收集、预览确认、创建单据、生成 Release Note、建立关联、失败补偿。

每一条规则写进去时都理由充分——「防新人跳过预览直接建单」「防建完单忘了挂关联」。问题在于，锁一把把往上加，加到最后连查个单据状态这种五秒钟的只读小事，模型都得先在脑子里通读半本《企业发布管理条例》。

内部评审拉过一组很直观的趋势：提示词总字数在涨、`NEVER` 禁令条数在涨、条件分支数在涨——三个指标叠在一起的结果，就是规则的漏遵循率跟着一起涨。更微妙的是规则互搏：前脚严令「写操作前必须完整预览全部字段」，后脚叮嘱「简单查询直接作答别绕弯路」，模型夹在两套语气强硬的指令中间进退失据，注意力被大量无关分支稀释。所谓「Skill 越写越多，Agent 越用越傻」，不是模型退化了，是你往它工位上堆的无关公文太多了。

## 按意图频率和事务边界拆，不按命令数量拆

给肥胖的 Skill 减重，曾有人提议把长文档拆成主文件加一堆 `references/` 子文件。这招如果没想清楚触发条件，很容易变成数字游戏：文件确实短了，但只要入口路由含糊，模型为了稳妥还是会把子文件挨个读进来——从「一口气吞一斤」变成「分五口吞一斤」，认知预算一分钱没省。真正省预算靠的是**不读**，不是分批读。

最后落地的拆分准则是两条：**按意图频率分层，按事务生命周期划界**。

![skill 拆分](https://bugyalu-1307401873.cos.ap-guangzhou.myqcloud.com/typora/skill-split-map.png)

1. **通用薄 Skill 只留高频原子路径**：日常九成以上的 `read / search` 和单字段更新留在主 Skill 里，关于创建流程只留一句干净利落的硬路由——「一旦识别到 `create Story` 意图，立即打包已解析上下文转交专属 workflow，禁止原地执行」。主 Skill 不再复述下游的字段细节，只管触发条件、禁绕过红线与返回契约。
2. **低频长事务整包收进 Workflow Skill**：跨步骤、强顺序、带外部副作用的创建链路整体迁入独立 workflow，在显式的运行状态里记录阶段进度、幂等键、人工确认与外部单号，中途报错按阶段补偿或续跑，不再指望主 Agent 凭上下文记忆硬撑。

这里最忌讳按「命令个数」机械切分。比如把 `Release Note` 单独拆成一个平行 Skill 就是典型败招：它和 `create Story` 前半段的字段预览共享同一个业务事务，一旦拆离主流程，后半段的强制约束反而最容易被模型漏掉。「功能相近」不是放一起的理由，「同生共死的事务边界」才是——硬把同一桩事务剪成两半，等于把结婚证撕开各发给两个陌生人。

省预算时我们也踩过一次反向的坑，恰好给「按需加载」划出了底线：把 Slack 的消息排版规范从常驻 system prompt 挪进按需 Skill 后，工具描述里一句「普通短查询不要调用本工具」和发送职责撞了车——Agent 老老实实算完答案，然后选择了闭嘴不发。原因很朴素：在 Slack 渠道里，模型的普通文本输出对用户是不可见的，不调发送工具就等于没说话。后来我们把「普通输出不可见、首次外发前加载一次排版契约」写死成通道级规则才算收口：**排版细节可以按需省，但渠道交付契约不能省。**

## 怎么证明拆对了

重构 Skill 最怕停在「目录看着清爽多了」的自我感动上。上线前必须用三组回归用例把边界钉死：

- **防误触**：高频纯查询请求不会因为措辞擦边而误入昂贵的创建工作流；
- **防绕过**：触发创建 Story 时，100% 经过预览与 Release Note 阶段，不存在抄近道直写接口的漏网之鱼；
- **防重入**：Release Note 或关联步骤异常失败时，补偿与重试不会在下游悄悄建出第二个重复 Story。

把同一批真实请求在拆分前后跑一遍，盯住单次任务的累计输入 token、路由命中率与端到端完成率，账自然就清了。Skill 设计从来不是文档整理癖，而是一门精打细算的系统经济学：写进常驻入口的每一句话都是硬通货，动笔前先问自己一句——这条规则，真的值得让往后十万次毫不相干的查询跟着一起买单吗？
