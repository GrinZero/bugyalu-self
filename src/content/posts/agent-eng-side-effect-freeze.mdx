我对 Agent 系统里「任务成功」四个字彻底失去信任，源于两次挨得很近的线上现场。

第一次，QA Agent 接过一条 Slack 任务，跑完后编排层干脆利落地标了 `success`。我翻开执行轨迹：64 次工具调用，目标用例系统里一条记录都没写进去。细看更扎心——其中 20 次是参数一字不差的精确重复，占全部调用的 31.3%；重复返回往上下文里灌了约 1.62 MB 数据，占全部工具结果体积的 64.1%。模型吭哧吭哧查了半小时资料，把同一份文档复印二十份铺满桌子，然后拍拍手宣布收工。

第二次恰恰相反。批量写入走了逐条 fallback，10 条用例其实已经落进了目标系统，每条单项校验都过了，但没有任何一个环节登记「整批交付完成」。等 worker 重试时，它看了一眼 memory 里一句没头没尾的「已生成」，直接跳过写入。同一件活儿，第一遍干了没认账，第二遍认账了没干。

这两件事摆在一起，足够把一个朴素事实钉死在墙上：「模型说做完了」「接口返回 200」「workflow 跑到了终点」，是三个完全不同的状态，谁都不能单独证明外部世界真的按预期变了。

![三种成功互不担保](https://bugyalu-1307401873.cos.ap-guangzhou.myqcloud.com/typora/side-effect-freeze-three-states.png)

## 三种「成功」，互不担保

做 Agent 可靠性设计，第一步是把这三个常被混为一谈的信号拆开：

- **模型最终回答了「已完成」**：这是大模型的自我陈述，证据力约等于被告在法庭上宣布自己无罪。
- **工具调用拿到了 HTTP 200**：这是传输层的签收单，只证明对端受理了请求，不回答领域对象长对了没有。我们往 MeterSphere 写用例时就造出过一种「三合一残次品」——脑图里看得见、详情页打开空白、列表里归属到了错目录，同一条数据在三个视图里坏出三种花样，而接口全程礼貌地返回 `200 OK`。原因很简单：文字路径 `nodePath` 只是展示标签，决定实际归属的是叶子 `nodeId`；`steps` 少填一个序列化字段，详情页就罢工。只看传输层绿灯，模型就会心安理得地交差。
- **workflow 标了 completed**：这是编排图的状态，只说明流程走到了末端节点、没有中途崩盘；至于关键副作用有没有发生、发生了几次，它一概不管。

「到底写完没有」本质上不是阅读理解题，而是一道**对账题**：计划要写的集合 vs 外部世界实际落下的集合。默认拿模型回答或接口状态码当答案，系统迟早会在某个边界上安静地说谎。

## 把「写完没」改成确定性对账

想通这一点后，我把所有外部写入收敛进了一条确定性协议：**执行前冻结业务计划，写入后推进缓存纪元，再用新鲜读取逐项核销**。

![协议流程](https://bugyalu-1307401873.cos.ap-guangzhou.myqcloud.com/typora/side-effect-freeze-protocol.png)

整条链路由五个独立持久化的对象咬合而成，谁也不许顶替谁：

1. **证据快照与 `CasePlan` 冻结**：`dry-run` 通过后，立刻把证据快照摘要、请求载荷摘要、每条用例的规范身份、数量顺序，以及经过一致性互验的目标叶子 `nodeId + nodePath` 一起压进不可变的 `planHash`。执行路径可以走批量接口，也可以退化为逐条写入，但只准消费冻结计划里的条目；想改内容必须重新走 `dry-run` 签发新 hash，重试时也直接恢复持久化的 `CasePlan`，模型重新生成的候选集没有投票权。
2. **推进 `mutation epoch`（变更纪元）**：这步最容易漏，也最致命。写工具一旦执行，之前所有的读缓存都成了「旧世界的快照」。如果不推进 `mutation epoch` 把写前读缓存成批作废，后续验证就可能命中写前缓存，拿昨天的快照证明今天的施工——最隐蔽的 false green 就是这么来的。
3. **`fresh read` 逐对象回查**：验证阶段只接受当前 `mutation epoch` 之后发起的新鲜读取，而且不信批量接口笼统的聚合成功，逐条核对对象 ID、实际目录归属与核心字段。只有 `verifiedCount === plannedCount` 且领域不变式全部过关，才签发绑定 `planHash` 的完成回执（receipt）。
4. **拒绝把「部分成功」四舍五入**：计划写 10 条只验过 7 条，绝不签发 receipt，也不笼统标成「什么都没发生」让重试器盲目重写一遍。`partial success` 是独立于成功与失败之外的第三种状态——老老实实列出已落库对象、缺失项与待补偿清单，门禁不认感动分。

配套再补一本单次运行内的 **Evidence Ledger（证据账本）**，专门治开头那 20 次精确重复：`callKey` 对相同调用做并发 single-flight 合并；带版本号的 `sourceKey` 识别「换个参数写法查同一份资源」的语义重复，只向模型注入有界摘要与引用，把执行次数和灌进上下文的字节数一起管住。连续几轮既没产出新证据、也没推进 `mutation epoch` 时，`no-progress` 熔断器直接拉闸，不再陪模型空转。

## 把门禁建在模型摸不到的地方

协议设计对了，落点选错照样白搭。

第一版我走过一段弯路：在最外层套一个顶层 workflow，由包装层拉起 Durable Agent，等它跑完再从聊天记录（transcript）里反向抠出 `CasePlan` 去执行写入。Review 时越看越别扭——拿非结构化的对话轨迹当执行输入，等于从泥地脚印反推嫌疑人身份证号，重试和版本都对不上账；更糟的是职责打架，外层 workflow 觉得自己在管任务状态，里面的 Durable Agent 也觉得自己在管状态，两台状态机各记各的账，故障恢复时互相踩脚。

开放式推理和确定性副作用根本是两种不同的原语，不该共用一台状态机。

![Commit Tool 内部流程](https://bugyalu-1307401873.cos.ap-guangzhou.myqcloud.com/typora/freeze-receipt-flow.png)

后来我直接拆掉了那层外包装，把门禁沉进一个受控的 **Commit Tool** 里，同时将原始的底层写接口从模型的工具列表里彻底抹掉。模型视野里只剩两样东西：只读取证工具，以及这扇唯一的提交窄门。Commit Tool 接收结构化参数，在工具内部闭环跑完 `dry-run`、冻结 `CasePlan`、生成稳定 run ID、执行底层写入、推进 `mutation epoch`、完成 `fresh read` 对账并返回 receipt。

这里有个很顺手的角色降级：**计划不再来自模型的自由发挥，而来自可信代码对结构化入参的冻结**。模型从「拍胸脯说干完了的施工队长」，降格成了「在窗口递交申请表的申请人」——口头承诺没法审计，表格可以校验、可以拒收、可以留底。

## 这套协议不担保什么

把话说满容易翻车，这套机制的物理边界同样清楚。

首先，`planHash + fresh read` 解决的是**业务对账**，不是分布式理论里无条件的 `exactly-once`。如果外部接口已经写成功，但进程恰好在本地落盘 checkpoint 前崩溃，单靠稳定 run ID 堵不上这条裂缝。恢复时的正确动作不是闭眼重写，而是先做一次 `fresh read` 盘点对端已经落下了哪些条目，只补齐差集——这要求目标系统本身具备幂等键或唯一性约束配合。

其次，写后回查只对**状态可回读**的外部系统成立。如果副作用是发邮件、推消息或触发不可逆的外部动作，读回路径根本不存在，就得老老实实换用业务方签发的幂等回执、事务性 Outbox 或人工审批门禁，别硬套 `fresh read` 假装闭环；碰到最终一致的下游，回查还得配有界退避，不能写完毫秒级读不到就慌张重发。

说到底，给 Agent 接写权限的及格线只有一条：别让模型既当施工方又当监理。模型尽可以自信满满，但算不算写完，只能由那张对上 `planHash` 的回执说了算。
