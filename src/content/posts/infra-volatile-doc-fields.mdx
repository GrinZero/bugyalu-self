给 Agent 暴露数据接口时，我们很容易顺手把后端现成的内部对象直接 `JSON.stringify` 扔过边界，默认模型「用得上的自己留、用不上的自己忽略、该原样传的自己复制」。直到两起前后脚撞上的怪事，把我这个偷懒假设彻底治好了。

第一桩怪事出在回归验证上。`get_document` 是喂给 Agent 查原文的工具，下游缓存、去重和一致性比对都指望「同一个 citation 返回同一份内容」。我用最笨的办法测了一次：拿完全相同的参数对同一个引用连调两遍，然后 `diff` 两次响应。

结果第一眼就让人心里一紧：**两次返回的字节数差了约 14 KB。** 文档刚被人改了？检索节点状态不一致？

扒开 JSON 逐字段比对，真相既无聊又扎心——正文一个字没变，14 KB 的差额全出在两类「本来就不该稳定」的字段上：第一次响应里多带了一条 768 维的浮点数组 `summary_embedding`（单这一项就占了约 14 KB），第二次没带；另外正文里嵌着的 20 个私有 GCS 图片链接每次请求都会现场重签，V4 签名、时间戳和 3600 秒过期参数回回翻新。把内部向量剥掉、把签名查询参数归一化之后，两份响应的 SHA-256 分毫不差：11 个 chunk、25,239 字符正文、分页与引用关系完全一致。

虚惊一场，但顺着那 20 条几百字符长的 GCS 签名链接往下追，第二桩更疼的现场已经在前面等着了。

## 响应字段的三个阶层

那 14 KB 的幽灵差额，逼着我先把穿过工具边界的字段按「谁有权定义内容一致」划成三个阶层：

![响应字段的三个阶层](https://bugyalu-1307401873.cos.ap-guangzhou.myqcloud.com/typora/doc-fields-cover.png)

1. **内容身份层**：`chunks`、正文、`content_len`、分页游标、跨文档 `references` 以及稳定的业务元数据。只有这一层变了，才配叫「文档变了」，缓存键和回归哈希只该建立在它的白名单之上。
2. **检索内部副产物**：像 `summary_embedding` 这类高维向量。它是底层检索引擎算出来的中间导数，顺手搭了响应体的便车。把它漏进 Agent 工具返回值里是纯粹的败家——大模型读不懂 768 个浮点数，却得在接下来每一轮对话里为这 14 KB 乱码反复交上下文门票钱；更别提一旦消费方傻乎乎把它当必填字段解析，服务端哪次没返回就会直接炸出空指针。
3. **传输临时凭据**：带有效期的签名 URL。它不是资源的「身份证」，只是「这一小时有效的登机牌」。拿原始字节去做一致性比对，等于质问航空公司为什么今天和昨天的登机牌条形码不一样；反过来拿一刀切「删光所有 query 参数」去做归一化同样危险，因为有些系统恰恰把文档 ID 放在查询参数里——身份字段必须靠显式白名单认领，不能靠黑名单猜。

给字段分完阶层，前两个动作很顺手：Agent 侧接口默认裁掉全部内部向量，一致性校验只对规范化后的第一层字段算哈希。真正的硬骨头在第三层——既然签名 URL 是临时凭据，那它当初为什么要穿过模型的上下文？

## 512 个字符抄丢 2 个：模型不是 `memcpy`

把临时授权串交给大模型保管会有什么下场，我们的内部知识问答 Agent 用一次静默故障给出了标准答案。

那天员工在 Slack 私信里问了一条带操作指引图的人事流程问题。编排大盘显示主流程 `success`，文字回答也准时送达了，唯独配图人间蒸发。翻开子任务日志，图片上传接口躺着一个刺眼的 GCS `403 SignatureDoesNotMatch`。

我把知识库原始返回的 signed URL 粘进浏览器，200，图好端端的；再把 Agent 转手传给 Slack 上传工具的 URL 参数拉出来逐位比对——**GCS V4 签名用的是 2048 位 RSA，十六进制签名串固定 512 个字符；经过模型之手转抄一遍后，变成了 510 个。**

![512→510](https://bugyalu-1307401873.cos.ap-guangzhou.myqcloud.com/typora/hr-cover.png)

不多不少，刚好漏掉两个十六进制字符。人类肉眼扫过去跟原链接一模一样，但在密码学验签面前，差半个比特也是废品。

当时有人提议在提示词里加粗强调「请务必原样逐字符复制 URL，严禁修改」。这是最便宜也最无效的药方：**大模型的文本生成本质上是逐 token 的概率采样与重建，不是内存里的 `memcpy`**。让一个统计预测器去搬运几百位高熵密码学材料，就好比让速记员凭听觉默写一段 SHA-256——十次里抄对九次不叫可靠，叫还没轮到你出事。

这件事顺手帮我们立下了一条超越图片上传的通用铁律：**凡是要求逐字节保真、或者触及安全隔离边界的参数，一律不准过模型的手。** 不只是签名 URL 和访问 Token，像消息投递的目标 `channel`（防模型猜错一个字母把隐私回复发进别人私信）、多租户检索的 `tenant / datastore` 归属，统统必须由服务端上下文在工具内部直接注入，或者只让模型传递简短的逻辑句柄（如 `asset_id`），由确定性代码在后台完成换签与投递。模型负责决定「发什么」，代码负责守住「凭什么发、发给谁」。

## 无状态 HMAC 代理：把凭据留在最后半步

回到知识检索接口本身，想把又长又脆的 GCS 签名 URL 彻底请出模型与 Markdown 渲染链路，同时还不把私有存储桶敞开成公开访问，最后落地的方案是一层极薄的**无状态资源代理**。

![无状态 HMAC 资源代理](https://bugyalu-1307401873.cos.ap-guangzhou.myqcloud.com/typora/gcs-proxy-seq.png)

入库和返回给 Agent 的不再是带一串密码学尾巴的临时链接，而是稳定的短路径句柄 `/assets/<hmac>/<object-path>`。无论大模型在回答里怎么引用、Slack 和浏览器怎么渲染，手里攥着的始终都是这截几十个字符的干净路径。直到终端用户真正发起 `GET` 请求的那一刻，网关才在边界上重算路径 HMAC——但凡有人试图篡改 bucket 或对象路径，当场回 `404`；校验通过后，现场签发一张仅 10 分钟有效的 GCS V4 签名链接，通过 `302` 重定向把下载流量直接交还给对象存储，应用服务器自己不背一字节的图片带宽。

存量迁移走「写时规范化 + 读时兜底适配」双轨并行：新同步入库的文档直接落短路径，历史库里存量的 `gs://` 引用在 `search / answer / get_document` 出站前统一换算，既不用停机刷表，也不逼下游同时兼容新旧两套格式。

当然，天下没有白捡的省事。选无状态 HMAC 而不是在数据库里单建一张 `short_id → object_key` 映射表，是一笔算清楚了代价的买卖：

- **赚到的是零状态开销**：省掉了一张高频查询映射表的存储、缓存一致性与过期清理，任意节点拿到 URL 算一下哈希就能验真伪；
- **让渡的是单条吊销能力**：这种链接本质上是 capability URL（持链即访问），一旦外泄，在密钥轮换前无法单独废掉某一张图；而且签名密钥绝不能像普通环境变量那样粗暴替换——一旦直接换掉单密钥，历史消息里发出去的所有短链接会瞬间全站 `404`，轮换机制从第一天起就必须设计成带密钥版本号的双钥过渡（`v1/v2` 并行验签、新链统一用新钥签发）。

## 收个尾

回头把这两桩小案子叠在一起看，它们讲的其实是同一条接口卫生习惯：**API 响应不是数据库 dump，大模型也不是透明网线。**

一个字段在跨过模型边界之前，先拿三把尺子量一量——它是定义业务事实的内容身份，是只配留在后端的检索草稿，还是不该让概率模型代为保管的临时凭据？把 14 KB 的浮点数组拦在门外，省下的是真金白银的上下文预算；把 512 位的签名换成确定性短句柄，省下的是半夜对着 `403` 抓瞎的排障工时。
