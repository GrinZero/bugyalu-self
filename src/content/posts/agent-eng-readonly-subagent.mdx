做多源取证类的 Agent，迟早会走到拆分「主从结构」这一步。

一次常规的研发或测试定位，往往要翻 Jira 描述和评论、拉 GitHub PR diff、爬 Slack 讨论串，再去 Figma 对一眼设计标注。每个数据源动辄几轮调用起步，要是全往主 Agent 的上下文里硬塞，它还没来得及动脑子，光原始材料就把窗口淹没了。最顺理成章的解法是按数据源拆出一组子 Agent——各管一摊去读、过滤、去重，最后只把浓缩后的证据摘要交回主 Agent 拍板。

分工一划，紧跟着就是权限问题：这些子 Agent 是派出去抄情报的，绝不允许顺手对外发消息、改单据、写用例或点审批。听起来只是一句再朴素不过的「只读」需求，真往代码里落才发现，**要求模型「自觉不写」和让它在物理上「写不了」，完全是两码事**。

![两道防线](https://bugyalu-1307401873.cos.ap-guangzhou.myqcloud.com/typora/readonly-subagent-cover.png)

## 第一道防线：别让委派方替受托方写门禁

最早的一版原型踩过一个非常典型的坑：主 Agent 委派任务时，通过动态字段（`$fromAI`）顺手生成子 Agent 的 `System_Message`。

初看这招灵活得不行——主 Agent 可以根据现场情况给子 Agent「量身定制」人设。但放到安全视角下看，这等于让进门访客自己在保安亭印门禁卡。大模型并没有反骨，它只是忠实地优先响应最新鲜、最具体的上下文：平时主 Agent 老老实实传「请只读检索」，哪天碰上棘手任务甩过去一句「抓紧查清顺便把状态更一下」，只读铁律就在传输途中被悄无声息地覆盖了。

修法是把权限声明焊死在子 Agent 自身不可覆盖的系统层配置里，上游委派参数只准传「查什么」，碰不到「能干什么」：

- **默认拒绝模糊操作**：事先拉出明确的操作分类表——像 Figma 导出预览图、下载已有附件这类无外部状态变更的动作归入合法读取；凡是读写混合或拿不准副作用的操作，协议强制返回 `BLOCKED_SIDE_EFFECT`，把决策权原封不动踢回主 Agent。宁可误拦一次合法读取（代价只是一次重试），也不放过一次越权写入。
- **并发度限流**：单批最多并发拉起 2 个子 Agent，超出部分排队分批跑。这个数字不是压测调出来的性能甜点，而是给失控半径上的保险栓——放一群边界含糊的子 Agent 同时出门，跨源重复检索和死循环的概率会成倍放大。

即便把这些全做完，我也只敢管它叫「第一道防线」，而不是「只读方案」。方案假定自己不会出错，防线假定自己迟早会漏。

## 第二道防线：prompt 管意图，allowlist 才管能力

第一道防线最扎心的地方在于：子 Agent 嘴上背熟了八荣八耻，底层挂载的却还是那套读写俱全的共享工具集。

**Prompt 约束的永远只是意图，工具面决定的才是物理能力。** 把「绝对只读」写进提示词一百遍，本质上还是贴在公司茶水间墙上的「请勿拿走他人酸奶」——防得住守规矩的体面人，防不住提示词注入、长上下文注意力漂移，或者模型某次单纯的理解跑偏。涉密机房禁止拍照，靠的从来不是员工手册第三章，而是门口那排必须存手机的铁皮柜。

![两道防线的分工](https://bugyalu-1307401873.cos.ap-guangzhou.myqcloud.com/typora/readonly-subagent-two-walls.png)

所以第二道防线必须是**工具级的最小权限隔离**：给每个子 Agent 挂载独立的只读 Tool Allowlist（或只读沙箱实例），让所有带写副作用的 API 从它的工具 schema 里彻底蒸发。模型压根看不见锤子，自然也就没机会乱砸钉子。

物理裁剪还附赠了一笔意外之财：**省认知预算**。工具列表里混着一堆写接口时，子 Agent 每次调工具前还得花注意力判断「这玩意儿算不算副作用」；把写工具直接端走后，分类纠结归零，漏判率也跟着归零。安全工程里最牢靠的规则，永远是那种根本不需要靠自律去执行的规则。

## 一次差点开错刀的误诊：回传没断，是边界漏了

这套父子架构跑起来后，出过一起很有教材价值的线上疑案。

最开始报上来的症状叫「子 Agent 结果没回传」：某次任务跑了很久，主 Agent 像没收到下属汇报一样在原地自言自语，当时甚至有人准备动手重构父子节点的工具返回通道了。

我先把现场摁住没让动刀，调出完整的执行日志逐帧核对。其中一条完整跑完的记录里，一共触发了 4 次子 Agent 委派、55 轮大模型调用，耗时约 30 分钟——底层的 `tool result` 回传链路完好无损，子 Agent 产出的文本一字不落地递回了主 Agent。而那条被当成「断连铁证」的样本，真相让人哭笑不得：当时两个子 Agent 正在过宽的循环里打转没收敛，用户等不及手动点了取消。**拿一条半路被拔掉电源的执行去证明通信断连，无异于拔了病人的氧气管，再向家属宣布病人原本就不会呼吸。**

更值得警醒的代价藏在那条跑完的日志末尾：通信一分不差，但属于需求 `FIN-7119` 的 8 条用例，被整整齐齐写进了一个八竿子打不着的业务模块里。好比顺丰物流轨迹全程绿灯、签收单字迹工整，推开门一看，快递端端正正摆在邻居家鞋柜里。

![执行解剖](https://bugyalu-1307401873.cos.ap-guangzhou.myqcloud.com/typora/subagent-boundary.png)

剥开表象，真正的病根是三道失守的边界叠在了一起：

1. **迭代上限放得太松**：主 Agent `maxIterations` 设到了 80，子 Agent 设到了 50。证据不足时，宽松的配额直接纵容模型在原地盲目空转；
2. **数据源职责串味**：负责 Slack 的子 Agent 顺手跨界去捞了 Jira 的单据，多路重复取证拖慢了收敛，才诱发了用户的手动取消；
3. **写前缺领域不变式校验**：主 Agent 拿到汇总后调写入接口时，没人核对目标目录 `node_path` 与当前 Jira 单号的业务归属关系，8 条用例就这么堂而皇之地落错了户。

三件事里没有一件怪得上「底层连接坏了」，全是因为边界画得太虚。要是不看日志顺着直觉去「修通信层」，非但治不好 55 轮空转和错写目录，还得凭空引出一堆新回归。定位清楚后，真正的处方反而非常朴素：把子 Agent 迭代上限压回 12～15 轮、主 Agent 压回 30 轮以内；按数据源钉死各自的工具白名单禁止串门；在主 Agent 唯一的写入出口补上目标目录与需求单号的硬校验，对不上直接拒写。

那次排障也给我留下一条固定习惯：往后凡是碰到多 Agent 系统报「没返回」「没生效」，动手改代码前先拿日志把现场分进四个抽屉——**通道真断了、循环还在转没收敛、中途被人或超时掐了、结果回来了但下游写歪了**。四种病共用同一副面孔，药方却南辕北辙。

## 留下的不等式

回头看，只读子 Agent 的全部经验可以压成一个很直白的不等式：

**主 Agent 嘱咐它只读 ≠ 子 Agent 承诺自己只读 ≠ 子 Agent 在物理上只能读。**

提示词写得再严厉，也只是君子协定；架构图画得再干净，也挡不住共享工具集里顺手摸到的那把写接口。把「能做什么」锁死在不可覆盖的工具白名单与凭证隔离里，再把「该关注什么」交给提示词去引导——两条腿都站稳了，「只读」才不是贴在系统墙上的一张许愿帖。
