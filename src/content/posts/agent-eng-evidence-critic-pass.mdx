做内部 QA Agent 架构评审时，最让我后背发凉的一份材料不是报错日志，而是两份「全都顺利完成」的执行记录。

同一个需求单 `FIN-6202`，同一个 Agent，前后脚跑两遍：第一遍吐出 10 条测试用例，第二遍吐出 12 条。条数差两行倒在其次，细对内容才叫热闹——模块命名对不上，拆分粒度对不上，同一段结算逻辑第一遍拆成两条独立用例，第二遍揉成了一条大杂烩；遇到 Figma 节点名和 Jira 标题叫法不一致的地方，两遍各自悄悄押了一头，谁也没吭声。

最要命的是，如果你把任何一份单独拎出去评审，它们都写得人模狗样：步骤工整、断言流畅、术语地道，完全过得了「看着挺专业」的肉眼初筛。只有把两份并排摆在同一张桌子上，你才看得出对面坐着两个平行宇宙里的测试计划。

**把随机性包装成专业感，比直接抛异常危险十倍。** 异常至少会报警，而这种「单看都成立、合看互拆台」的漂移只会一寸寸吃掉团队对 Agent 的信任。病因其实很清楚：模型从来不缺「编用例」的文笔，缺的是下笔之前的**证据治理**。

## 生成不稳定是表象，五路原料一锅炖才是病根

顺着生成链路往上摸，QA Agent 吃的原始材料来自五个脾气迥异的地方：Jira 需求单、Figma 设计稿、代码变更、Slack 讨论串，再加上从历史库召回的过往测试经验。

初版架构干的事很粗暴：把五路材料一股脑塞进同一个长 prompt，让大模型一次性消化并直接写出最终用例。大模型的长处恰恰成了祸根——它太擅长「无痕缝合」了，事实、推断与猜测在输出里穿上了同一套西装：

- **跨源冲突被静默吞掉**：Figma 上的按钮叫一个名，Jira 描述里叫另一个名。真人测试工程师看到这儿会停下来拉群问一句「以哪个为准」，模型不会——上下文里谁先露面或者哪边词频高，它就顺手按哪边统一了，跑两遍自然押出两种结果。
- **风险假设篡位成硬预期**：历史经验库召回了一条提示——「导出超过一万行可能会走异步任务」。这原本是一条待核实的**历史经验猜测**，结果模型大笔一挥，把它写成了和 PRD 明确条文平起平坐的硬断言。测试人员真拿它当准绳去验，测出来的「缺陷」其实是系统根本没这么设计。
- **多触发条件被糊成一团**：为了凑篇幅整洁，模型动不动把三四种异常分支合并进一条「综合异常校验」，字面上什么都提到了，真到执行时连先测哪一步都分不清。

面对这锅粥，评审会上最容易冒出来的三种「快修」全被我否了：继续往单 prompt 里塞格式铁律（规则越长漏遵循率越高）、硬卡输出条数上限（只会逼模型把更多分支硬揉进单条用例）、或者再多接几个检索工具（账本都没有，进货越多仓库越乱）。它们犯的是同一个错——把「原料没分级」当成了「厨师刀工不好」。

## 在下笔之前，先给证据上户口

重做之后的链路，核心原则只有一条：**禁止模型直接把多源原始材料一步翻译成入库用例**。

首先在最前头立一道轻量的 **Intent Router（意图路由）**。以前用户哪怕在群里随口问句「在吗」或者查个简单状态，整条重型 QA 链路照样披挂上阵，光测试方法论提示词就先烧掉约 1.7 万 token，既贵又容易让模型在无关规则里犯迷糊。路由前置后，寒暄与轻量问答直接走短路径，真正的需求分析才进主干流水线：`Evidence Model → QA Planner → Critic Pass → Writer`。

![证据条目与覆盖矩阵](https://bugyalu-1307401873.cos.ap-guangzhou.myqcloud.com/typora/evidence-model-schema.png)

真正镇住随机性的是中间这三棒交接：

1. **Evidence Model（结构化证据登记）**：第一棒只管「认账」，不准写用例。它把五路材料拆解成带稳定编号、来源定位与置信度的结构化条目——板上钉钉的需求原文记为事实 `F01`（例如「月末锁定后结算单只读」）；历史经验推演记为风险 `R03`（例如「万行导出可能转异步」），状态显式打上 `needs-confirmation`，从 schema 层封死「猜测混充事实」的通道；Figma 与 Jira 叫法打架的地方单独单列为冲突 `C02`，状态标为 `pending-human`，严禁模型私自替产品经理拍板。
2. **QA Planner（受控规划）**：第二棒生成候选用例时，每条 case 必须显式挂靠它所覆盖的 `F* / R*` 编号。这个看似不起眼的外键引用，直接把「两遍结果怎么长得不一样」从文学鉴赏题变成了集合运算——第一遍覆盖了 `{F01, F02, R01}`，第二遍覆盖了 `{F01, R01, R03}`，漏了哪条证据、多算了哪个风险，做个差集一目了然。反过来，任何一条说不出自己站在哪个 `F/R` 上的野生用例，直接没有存在资格。
3. **Critic Pass（独立二审）**：候选用例进库前必须过一遍独立审查官，专挑六类硬伤：**遗漏**（无人认领的 `F/R`）、**重复**（两条用例测同一件事）、**越位**（把 `needs-confirmation` 的风险假设写成了板上钉钉的预期结果）、**粒度过粗**（多个独立触发条件揉进单条）、**不可观测**（断言写得漂亮但在测试界面或接口上根本看不见），以及**优先级倒挂**。前两项靠覆盖矩阵就能机械卡死，后四项专门逼问「它作为一条真实测试到底能不能跑通」。

只有闯过 Critic 的规范用例集，才允许交到下游 Writer 手里（再接上写前冻结 `CasePlan` 与写后对账）。模型觉得写得好不算好，过得了户口核验与二审岗哨才算数。

## 给审查官自己也套上回归基准

引入 Critic 之后，紧跟着就会冒出那个经典的套娃问题：谁来监督审查官自己不抽风？

如果 Critic 拦得太松，0% 拦截率等于虚设岗哨；如果拦得太疯，把正常用例全毙了，流水线就彻底瘫痪。光看「跑通了没有」验证不了这套架构，验收标准必须换成三条硬口径：

- **同源回放收敛性**：同一份需求快照连跑多次，用例集合的模块归属与 `F/R` 覆盖映射必须收敛；即便存在细微表述差异，也必须能追回具体的证据条目，而不是归咎于「模型今天的手气」。
- **逐条可追问性**：随便从库里抽一条生成的用例，系统必须能顺着结构化字段一路答出它验证哪条 `F/R`、出自哪份原始文档、置信度几何、头上有没有未决冲突 `C*`。
- **Golden Dataset 回归评分**：我们把 18 段真实业务 QA 会话清洗沉淀成 32 条 Golden Case，配套逐条人工标注与分项 Scorer——把「关键测试点覆盖率」「禁止行为触碰率（如把猜测当事实）」「执行轨迹可信度」拆成三张独立打分表放进回归流水线。

这一步做完，审查标准才算真正从「某次评审时我脑子里的直觉」，变成了可回放、可 diff、改一行提示词就能立刻看到涨跌的工程资产。毕竟，一个帮忙抓别人代码 bug 的 Agent，总得先证明自己的判断不是掷骰子掷出来的。
